## Agreed migration behavior

Owner decision (2026-11-08): migration is restartable from the untouched encrypted backup, never resumable. Each attempt writes a fresh encrypted destination and verifies every entry before reporting success. After interruption, discard the identifiable incomplete destination and restart from the same backup. No checkpoints, progress database, partially imported rows, or resume metadata are needed. The backup is read-only to the migrator and is never overwritten, rekeyed or automatically deleted. This decision selects migration behavior; it does not select A, B or C.

## Migration algorithm (design, not executable code)

1. Ask user to close the old application and pause any external writers. Select the file locally. Detect hot journal/WAL state and refuse a casual main-file-only copy. Recovery must use the right SQLCipher engine against a controlled snapshot/backup set; do not rename/delete recovery files or use SQLite `immutable=1` to bypass recovery.
2. For a clean, closed vault, create a byte-identical encrypted backup with exclusive creation and user-only permissions, verify its hash, then use a working copy derived from that preserved backup for every attempt. Keep both the original and the encrypted backup unchanged. Never create a new backup from a partial destination. Reject symlinks, hard-linked vault aliases and unsafe destinations and never overwrite an existing destination. No master password or record values in CLI arguments, environment variables, telemetry, logs or CI.
3. Open the working copy read-only with a verified SQLCipher build. Key through the C API; set the selected compatibility parameters in documented order before the first DB read. Try explicit profiles 3 and 4 on separate handles; no heuristic write/migration. Verify by reading schema and content. A wrong password and damaged file can produce the same error; do not present every failure as a password mistake. If neither profile works, stop and diagnose exact historic build/settings locally.
4. Run schema/column/type validation plus complete cipher and SQLite integrity checks. Unexpected tables/columns/types must halt for a revised mapping; do not silently drop data. Preserve IDs, sqlite sequence behavior, all seven columns, nulls, empty strings, exact strings and integer values. Do not normalize master-password Unicode or reinterpret historic raw-key conventions.
5. A/B: create a new SQLCipher 4 destination with a separately initialized key/profile, memory temporary storage, encryption asserted before writes, and no plaintext header. Use a reviewed export/copy path, explicitly preserving schema/version metadata not copied by `sqlcipher_export`. Prefer two independent handles and bound row transfer if `ATTACH` key handling would require interpolated secrets. Build new schema/version transactionally; new writes use SQLCipher 4 profile only. Never run in-place `cipher_migrate` on the original. C: map to KDBX as described in OPTIONS. Use versioned typed/base64 encrypted metadata for IDs, timestamps and null flags only. Reject strings the native fields cannot retain byte-exactly; do not duplicate secret strings into archival custom metadata that would become stale after edits.
6. Commit, close and reopen destination with the same shipping engine. Read every row and compare all fields in memory to the source, in deterministic ID order. A/B additionally verify table definitions and next ID behavior; C verify native fields plus lossless metadata with KeePassXC and an independent reader. A count or checksum alone is insufficient. Persistent reports contain only counts, version/profile and pass/fail, not plaintext or unkeyed hashes of low-entropy secrets.
7. Flush completed encrypted destination and perform same-filesystem atomic no-replace finalization from a private temporary pathname to a new final pathname, with durable directory handling appropriate to macOS (for example, a reviewed `renameatx_np` exclusive-rename path). A prior existence check followed by ordinary overwriting rename is insufficient. Use directory/file descriptors and no-follow/identity checks to bound path races. An existing final destination is an error. At every failure, original/backup remains intact. After interruption, discard only the identifiable incomplete destination (including its associated transient journal/save artifacts once handles are closed), create a fresh encrypted destination, and restart the full import from the preserved backup. Do not inspect imported rows to resume or save checkpoints. If interruption occurs around final publication, do not infer success from file existence; require complete reopen/every-entry verification, or discard the owned unpublished candidate and restart. Never delete an unrelated pre-existing file. Simulate interruption at these boundaries.
8. Show completion only after successful independent reopen/compare. Do not delete the legacy vault automatically. A backup containing old passwords remains valuable to an attacker even after master-password rotation; explain its retention and let the user manage it locally.

Master-password change should use copy/verify and deliberate atomic replacement for A/B; unlike migration finalization, rotation intentionally replaces an existing path. Use fresh destination salt, verify old password fails on the new file, and document that old backups are still decryptable with the old password. No plaintext recovery key sidecar.

## Single-file semantics and writes

One file is the portable committed vault, not a promise that a crash-safe database never creates an auxiliary file. A/B use `journal_mode=DELETE`, full synchronization, `temp_store=MEMORY` and suitable build-time temp-store configuration. No WAL mode in v1. Encrypted rollback journals may exist during writes or after a crash; recovery must finish before a vault is copied. No permanent plaintext indexes/caches/settings containing vault contents. UI settings may exist outside the vault only if nonsecret.

Ordinary A/B CRUD uses SQLCipher/SQLite transactions and SQLite’s built-in journal recovery, with no custom recovery log, replay mechanism or application recovery state machine. Check transaction errors and let the database commit or roll back atomically; test interrupted transactions through the standard engine path. Use bound values and a serialized writer; edits use an expected revision to reject stale updates. Deletes remove active rows; encrypted pages/free space, old copies, snapshots and backups can retain old values. C uses upstream atomic encrypted saves, which must be verified in the target build. Encrypted temporary outputs/backup files are allowed for saves/migration but must never be required as a decryption secret. If “single file” means no auxiliary file even during updates, A/B's proposed SQLite policy does not satisfy that stricter constraint.

No concurrent sync merge is promised. Keep the active vault on a local filesystem; copy a closed, consistent file for backup. Detect external replacement/stale sessions before save. Filesystem/advisory locks do not coordinate independent cloud sync clients; conflict copies must be preserved and reconciled explicitly.

## Vault ownership and replacement protocol (A/B)

Before enabling normal edits, implement one owning process per canonical vault, shared across all windows. An application-level ownership coordinator, independent of the replaceable vault inode, must cover open, backup, restore, rotation and close. A transient nonsecret coordination artifact is permitted by the portable-single-file definition. Choose a robust OS primitive and demonstrate multi-process/alias behavior in the spike; absence of ownership proof means restore/rotation is disabled. Third-party writers and sync clients cannot be assumed to honor this lock.

For deliberate replacement: acquire exclusive ownership, reject new operations, invalidate session generation, drain/finish or roll back transactions, close every handle, verify source identity and destination immediately before replacement, then durably replace with the verified encrypted new file. Retain a verified encrypted rollback copy until durability is established. Reopen only with a new session generation and invalidate all old handles/tokens. Never rename an in-use SQLite database; an old-inode lock is insufficient. Test second-process access, path replacement, hard-link aliases and crashes across these steps. Ordinary migrations finalize at a fresh path and never replace the original.
