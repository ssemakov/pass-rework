# Rework options — 2026-11-08

Status: proposal; adversarial review and dispositions accompany this document. No implementation selected.

## Requirements and assumptions

- Create, search, reveal/copy, edit, delete, change master password, manual lock, automatic lock, and encrypted backup/restore.
- One portable encrypted vault file; no account, network service, or mandatory Keychain dependency to decrypt it.
- Existing DB compatibility or a verified, non-destructive migration. No plaintext export on disk. Agreed migration behavior: preserve the encrypted backup untouched; create a fresh encrypted destination; verify every entry; discard interrupted/incomplete output and restart from the backup. No checkpoints or resume support.
- Agreed Option A scope: minimum macOS 15 (Sequoia), with v1 compatibility tested on macOS 15 and 26. No older-version requirement. For like-for-like comparison, B/D and the C pilot use the same 15/26 acceptance matrix as a planning assumption, not a separate user commitment. Intel x86_64 and Apple Silicon arm64 remain proposed targets where the OS/hardware supports them.
- V1 release support policy: test macOS 15 and 26 explicitly, with an available next beta/RC as a separate exploratory lane. Do not expand v1 to a historical OS matrix. Test both CPU architectures where Apple supports them. Build SDK versions and deployment targets are separate; dependency updates must not silently raise the latter. Future Apple releases cannot be guaranteed in advance. Release notes must distinguish build/deployment floor, tested OS/CPU combinations and security-supported OS versions; a runnable old OS with an unpatched WebKit is not a security-support claim.
- External paid human security review is omitted from v1 by owner decision. Encryption/migration tests and adversary-agent reviews remain required; no audit/certification claim is made.
- No cloud sync or browser extension in a custom-app v1. Local concurrent opens and externally replaced vaults must fail safely. Encryption cannot prevent malware reading an unlocked vault, offline password guessing, or replacement with a valid older vault.

## Comparison

| Option | Stack and storage | Legacy path | Best fit | Main cost/risk |
|---|---|---|---|---|
| A: native Pass | Swift 6 language/toolchain, SwiftUI with AppKit integration, direct SQLCipher C API; stable SQLCipher 4 file | Read legacy profiles; migrate to a new encrypted file | macOS is the product, bespoke UI matters | Own the full app and security lifecycle; Swift UI copies of secrets |
| B: portable Pass | Tauri 2, Rust vault service, React + TypeScript + Vite, bundled SQLCipher through a reviewed Rust binding | Same migration contract as A | Future Linux/Windows support and existing React skills | WebView/IPC attack surface plus Rust/C packaging |
| C: adopt KeePassXC | Maintained upstream C++/Qt desktop app; KDBX 4 + Argon2id; small migration utility in this repo | One-way SQLCipher-to-KDBX conversion | Lowest ongoing ownership and mature CRUD | New UX and format; importer still security-sensitive |
| D: Go Pass | Wails 3, Go vault service, React + TypeScript + Vite, SQLCipher through CGo | Same migration contract as A/B | Custom React UI and a Go backend | Go/JS secret copies, bridge authorization and native CGo packaging |

Provisional preference: **A for a bespoke macOS replacement; C if maintaining a bespoke manager is optional. B if cross-platform and Rust are preferred; D if a custom React UI and Go are preferred.** A, B and D share storage deliberately: choosing a UI should not force inventing a new cryptographic format. C provides a materially different storage and maintenance strategy. [UI compatibility and comparability](UI-COMPARISON.md) separates workflow fidelity, native behavior and implementation effort; B and D can present essentially the same React interface.

## A — SwiftUI/AppKit + SQLCipher

Keep the relational data model. Replace Electron, Flow, Redux, Knex and the Node native module with a small Swift package for vault operations and a native app. Use an isolated vault actor to serialize access; C API calls use explicit error checks and bound SQL values. Pass key bytes via `sqlite3_key` rather than SQL interpolation. Link only the chosen SQLCipher SQLite implementation, and verify the packaged binary does not resolve storage calls to system SQLite. The risk is silent plaintext creation: ordinary SQLite ignores an unknown `PRAGMA key`. A SQLCipher-specific `sqlite3_key` call should make missing cipher linkage fail at build/load time; packaged-app reopen and plain-SQLite rejection tests still verify the actual behavior. This is a build/configuration risk, not a claimed SQLCipher vulnerability.

List responses omit passwords. Reveal only on demand; copy via native clipboard code. An actor is concurrency isolation, not a security sandbox. A compromised app can access unlocked secrets. Disable secret-bearing window/scene restoration, document autosave, preferences and crash-report capture. Inventory accessibility and window-preview exposure; E5/E9 must exercise restoration and OS lifecycle paths. Do not promise complete Swift `String` erasure; minimize lifetimes/copies and clear editor state at lock. Close DB handles, cancel pending work and invalidate session tokens on idle, screen lock, sleep and manual lock. A native session coordinator must atomically invalidate the session generation at lock request, outside the potentially busy vault actor, conceal UI and reject new operations. Check generation before reads and again at delivery. Interrupt long DB work where safe with the SQLite API; Swift task cancellation alone cannot interrupt C work. Define a measured lock-latency budget in the spike. In-flight transactions either finish atomically before final acknowledgment or roll back; UI concealment precedes storage cleanup, and full lock is acknowledged only after handles close and secret-bearing work is drained. Test KDF, integrity checks and CRUD during lock. Clipboard clearing must only clear content this app still owns; users can disable copying if Universal Clipboard propagation is unacceptable.

Use a pinned SQLCipher 4 stable build; the current upstream stable release observed is [4.20.0](https://github.com/sqlcipher/sqlcipher/releases/tag/v4.20.0). Confirm the Swift package/build recipe resolves that exact reviewed source and provider; do not accept a wrapper's ordinary SQLite fallback. On Apple, prefer the supported CommonCrypto build path. SQLCipher 5 is currently beta and changes the storage format; do not base v1 on it ([upstream announcement](https://www.zetetic.net/blog/)).

Normal edits/deletes use SQLCipher/SQLite transactions and standard journal recovery; do not add a custom recovery mechanism. Migration is an independent restart-from-backup operation. The new vault keeps the legacy columns and IDs, with a transactional schema version for future evolution. Legacy files open in a bounded import/read-only mode first; normal editing uses the verified new file. Direct legacy read/write mode is possible but not recommended because it perpetuates weaker KDF settings and increases the test matrix. Modernized files will not open in the old app.

Build with a current supported Xcode on macOS. Use SDK availability checks for APIs newer than the deployment target. Ship signed, hardened-runtime, notarized and stapled universal binaries (or separately verified architecture packages); verify every native dependency's architecture and minimum OS. Distribution signing proves publisher identity, not storage encryption. Disable network access in app design; defer updater code until its signing/update path is designed. Existing macOS CI images do not prove older OS behavior; use VMs or physical test machines for the matrix.

Effort: medium-to-high initial work, moderate continuing maintenance. First spike: packaged SQLCipher linkage, legacy fixtures, CRUD, crash recovery and lock lifecycle on both CPU architectures before investing in UI polish. V1 requires the documented tests and adversary-agent review; an external human audit is not a v1 gate.

## B — Tauri 2 + Rust + TypeScript + SQLCipher

Reuse concepts from the React UI, not the insecure renderer/storage wiring. Put all keys, SQL, vault lifecycle and copying in Rust. Bundle a pinned SQLCipher build; inspect the Rust binding's actual SQLCipher source/provider version and avoid accidental dual linkage to SQLite. No generic frontend SQL, shell, filesystem or HTTP capability. Expose narrowly typed commands: unlock, list metadata, create, edit, delete, reveal, copy and lock. Restrict paths to a user-chosen vault handle; reject arbitrary path/SQL inputs. Validate commands in Rust even if frontend validation exists. Register the vault command list with `tauri_build::AppManifest::commands` and grant explicit per-window permissions: plugin capability files alone do not restrict custom commands. Enforce command scopes in Rust; test denied calls from every unauthorized window/origin. Encode all SQLite 64-bit IDs/timestamps/revisions as validated decimal strings across IPC to avoid JavaScript number rounding; test values beyond 2^53.

Frontend runs bundled local assets only, with a restrictive CSP, no remote navigation, no HTML rendering from vault values, and least-privilege Tauri capabilities. List/search never returns passwords. A native secure unlock dialog is preferred if feasible; otherwise password entry transiently exists in JS, which must be explicitly included in the threat model. Even with native unlock, a compromised authorized WebView could invoke permitted reveal/copy commands: capability rules alone cannot prevent this. For v1, explicitly exclude compromised authorized frontend execution from the unlocked-vault confidentiality/integrity guarantee: list-plus-reveal can extract a vault even without bulk export, and permitted edits/deletes can alter it. Keep migration, master-password change and backup destination selection in native flows; frontend-supplied output paths are forbidden. Native per-operation consent can be evaluated if resistance to frontend compromise becomes a requirement. Keep v1 without bulk export APIs. One Rust owner enforces monotonic idle timing, a bounded queue, native sleep/screen-lock events and session generations. Invalidate generations immediately at lock request; check before secret responses and clipboard writes, cancel queued work, and acknowledge full lock only after transactions finish/roll back and all handles close. Clear UI fields and explicitly acknowledge JS/WebView strings cannot be reliably zeroized.

Use the same SQLCipher file policy, restart-from-backup migration and evidence gates as A. Normal edit/delete safety comes from database transactions and built-in journal recovery, without custom recovery logic. Tauri's [documented default macOS floor](https://v2.tauri.app/distribute/macos-application-bundle/) is 10.13; that is not this app's support promise. Use the comparison’s 15/26 test scope; the complete Rust, SQLCipher/provider, plugin and WebKit bundle must pass it. Test on real target OS versions, not only a recent WebView or headless browser. Same signing/notarization and native-library checks as A. WebKit security fixes follow the OS update lifecycle.

Effort: high initial integration work and more dependencies than A, offset if multiple desktop platforms are needed. First spike: packaged SQLCipher compatibility, adversarial IPC/path validation, stale-response rejection and WebKit testing. Rust reduces some memory mistakes; it does not establish confidentiality against an authorized malicious frontend or unsafe C code.

## C — migrate to KeePassXC / KDBX 4

Use upstream KeePassXC rather than fork a password manager. This repo owns a small offline migration utility, tests, release evidence and instructions. Existing upstream GUI supplies edit/delete, generator and lock behavior; configure clipboard timeout, auto-lock, history and recycle-bin retention explicitly. Disable optional browser/network integrations for the initial pilot. Verify the finished KDBX opens on a clean account/machine with only the file and master password; no local remembered key is required. If bespoke branding/UI is mandatory, this option does not meet that preference.

Current [official downloads](https://keepassxc.org/download/) advertise KeePassXC 2.8.0 for macOS 12+ with Intel and Apple Silicon packages. Verify the selected release, signature and actual target OS before rollout. Test latest/prior macOS and next beta as above; upstream support and Apple changes remain dependencies. Do not freeze an obsolete client to claim indefinite compatibility.

Convert in memory from read-only legacy SQLCipher to **KDBX 4 with AES-256 and Argon2id**, using an existing KDBX implementation or reviewed upstream serialization code, never a new crypto implementation. Candidate implementation/library and exact release must be selected and evaluated with tests and adversary-agent review in the first spike; this is an unresolved gate, not a claim that any Rust KDBX crate is audited. Prefer a small isolated utility that can reuse upstream code, subject to license review. Reusing GPL code can require GPL distribution of the utility; do not silently add it under the repository's MIT license. No CSV/XML plaintext file workaround.

Map `name/login/password/url` to Title/UserName/Password/URL. Preserve integer ID, exact timestamps with millisecond precision and null-vs-empty distinctions in a versioned, typed metadata envelope encoded as base64 in encrypted custom data; native KDBX timestamps can lose subsecond precision. Store only IDs, timestamp representations and null flags there, never an archival duplicate of original passwords/field values. Label the envelope as immutable import provenance with a format version: after KeePassXC edits, its native fields are authoritative and this metadata must never be replayed over current values. It is not a live shadow schema; stock KeePassXC will not maintain custom legacy null/timestamp semantics on later edits. Reject migration of any string that the chosen native KDBX/KeePassXC fields cannot round-trip byte-exactly, including XML-disallowed/NUL control characters. Surface the unsupported field locally and stop; do not sanitize or silently drop it. Test duplicate titles, valid Unicode, control characters, long values, nulls and unusual timestamp values. Reopen with the actual KeePassXC release and compare all fields through an independent read path before declaring success. Migration is one-way; the original encrypted vault remains a rollback artifact.

The [KDBX format specification](https://keepass.info/help/kb/kdbx.html) documents authenticated headers and ciphertext blocks, key derivation and public metadata. KDF parameters and file structure remain visible; vault contents are encrypted. Calibrate Argon2id on the slowest supported machine (initial candidate: 64 MiB, 3 iterations, parallelism 1; measured target roughly 0.5–1 second, then adjust and record). A malicious file's KDF/resource parameters require bounds before allocation. No key file is required for the single-file portability goal.

KeePassXC has [version-scoped security reviews](https://keepassxc.org/audits/): the 2023 review covers 2.7.4 source and the ANSSI certification listed there covers 2.7.9 on Windows 10. These do not certify the current macOS build or our importer. Match report scope to the chosen release and inspect changes. C has the strongest available independent review trail of the four; importer and target build still need validation.

Effort: lowest ongoing application work; importer complexity requires its own spike, tests and adversary-agent review; no commissioned human review is required for v1. First spike: select and license a KDBX writer that supports in-memory conversion, validate exact field round trips and cross-open with KeePassXC, inspect temporary files and atomic saves. If safe conversion requires plaintext disk staging, stop and choose a different route.

## D — Wails + Go + TypeScript + SQLCipher

[Wails](https://wails.io/concepts/architecture/) is a Go desktop framework with a web UI rendered in the OS WebView (WebKit on macOS). It is an alternative to Tauri, not a Go backend switch inside Tauri. Use the same React/TypeScript/Vite UI design as B; changing Rust to Go need not change the visible interface. Go owns SQLCipher access, key lifecycle, clipboard operations and native file selection. See [UI comparison](UI-COMPARISON.md) for the common v1 workflow and where native behavior requires extra work.

Version baseline observed on 2026-11-08: upstream’s stable [Wails 3.1.0](https://github.com/wailsapp/wails/releases/tag/v3.1.0); the [installation guide](https://wails.io/quick-start/installation/) requires Go 1.26+. Pin an exact supported Go patch, Wails Go module, CLI and matching frontend runtime in the spike. V3 has only recently reached stable; assess release/advisory fixes before selecting the final pin. Use the conventional native build path. V3.1’s experimental CGo-free GUI backend does not remove our SQLCipher CGo requirement and is out of scope for v1. Wails v2 is still maintained for critical updates, but is not the proposed new-app baseline.

**Storage:** use pinned SQLCipher 4 through a minimal reviewed Go/CGo bridge to its C API. Do not substitute an ordinary Go SQLite driver or invent a crypto layer. Select/implement the bridge in the first spike and prove actual linkage for each CPU. Prefer one explicitly owned C database handle for normal vault use (separate source/destination handles during migration), a serialized bounded worker and native parameter binding; no implicit `database/sql` connection pool in v1. Specify ownership of every CGo buffer: C must not retain pointers to Go memory beyond the allowed call lifetime; allocate C-owned buffers where retention is possible and free/wipe them at the documented boundary. Bind text/blob parameters with explicit byte lengths and `SQLITE_TRANSIENT` copy semantics; read text using `sqlite3_column_bytes`, not NUL-terminated C string helpers. Test embedded NUL, empty/null, Unicode and signed 64-bit boundaries without HTML normalization or truncation. Every newly opened handle must be keyed with an explicit byte length and have cipher settings/status verified before sensitive reads/writes. SQLite, rather than custom recovery logic, supplies normal edit/delete transactions and journal recovery. Use the agreed untouched-backup/fresh-destination/every-entry/restart migration, plus the shared ownership protocol for rotation/restore. The SQLCipher format/KDF is identical to A/B; Go does not strengthen the storage cipher.

**Bridge:** register a small facade service exposing only unlock, list/search metadata, create/edit/delete, reveal/copy and lock. Wails [service bindings](https://wails.io/features/bindings/services/) expose exported methods of registered services; never register the storage object or generic SQL/file/shell helpers. Inspect the actual callable method surface, not just generated TypeScript, and deny calls from unexpected origins/frames/windows. Exclude remote navigation, embedded untrusted pages, raw message handlers, server mode and LLM/MCP automation; production artifacts must exclude development/debug/control surfaces; bundle local assets, use a restrictive CSP and render record text without HTML interpretation. Native file flows own backup/import/rotation destinations, with no arbitrary frontend output path. Validate all inputs, lengths, explicit nulls and session authority in Go. Transfer 64-bit IDs/timestamps/revisions as validated decimal strings; migration stays entirely native.

**Lock and secrets:** one Go vault owner, monotonic backend idle timing, native sleep/screen-lock notifications and an atomic session generation. Invalidate the generation immediately on lock request, before waiting for the DB worker; reject queued work and check again at reveal/copy delivery. The frontend also compares its current generation after each awaited reveal/edit response, before updating the DOM; a backend check cannot recall an already queued JS result. Serialize clipboard generation check and write with lock invalidation so lock cannot slip between them. Go context cancellation does not automatically stop synchronous C calls: implement and test safe interruption/draining before final lock acknowledgment, with the same transaction policy as A/B. Password entry may transiently live in JS unless a native entry control is implemented; Go strings, serialization and garbage collection can create further copies. Minimize copies and disable logging/state persistence, but promise neither immediate heap erasure nor reliable Go/JS zeroization. No claim that Rust provides complete erasure either. As with B, a compromised authorized frontend can reveal or alter the unlocked vault; this is explicitly outside the v1 guarantee.

**Packaging/effort:** use the 15/26 matrix as the comparison assumption, on Intel/Apple Silicon where supported; verify CGo compiler/provider/linker settings and each native library’s deployment target. Build on macOS and sign, harden, notarize and staple the complete app as for A/B ([Wails macOS packaging](https://wails.io/guides/build/macos/)). Do not assume pure-Go cross-compilation or small demo bundle sizes apply to SQLCipher builds. Initial effort: medium-to-high, strongly dependent on Go experience; ongoing work includes Go, CGo, Wails, frontend and SQLCipher updates. First spike: exact shipping engine linkage, legacy migration, bridge denial tests, lock during C work and packaged WebKit behavior. D is a credible Go alternative, not yet an implemented or audited manager.

## Decision and delivery sequence

1. Owner selects direction; A’s minimum is macOS 15 and B/D use that scope as the comparison assumption; no product implementation before that decision.
2. Build storage/migration spike with synthetic fixtures and reproducible evidence from the selected shipping dependency versions. Do not handle a real vault in CI.
3. Implement custom CRUD/lifecycle for A/B/D or conversion UX for C. Define delete as removal from the active vault, not assured erasure from backups/APFS snapshots/history.
4. Run the encryption, migration, transaction interruption and macOS 15/26 gates, plus adversary-agent review of the chosen implementation. Resolve blocking findings. No external paid review is required for v1.
5. Pilot with a local backup and independent comparison. Owner decides merge and release.
