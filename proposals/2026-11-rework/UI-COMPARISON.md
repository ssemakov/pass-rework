# UI compatibility and comparability — A/B/C/D

This compares continuity with legacy Pass, native macOS behavior and the work needed to deliver the same v1 features. It is an architecture assessment, not a screenshot comparison, implemented UI or measured usability/performance study. Storage compatibility is a separate question: A/B/D share SQLCipher, while C migrates to KDBX.

## Legacy baseline

The inspected legacy app has a master-password unlock screen, an add button, a secret count, search and a list of entry cards. Cards show name, login, masked password and URL, with reveal/copy controls; adding uses those four fields. Search currently requires three characters and matches name/URL. These observations come from the pinned source, including [Home](https://github.com/ssemakov/pass/blob/7cd8c6c0bc395fa3676c151a84c1657cda8cb481/app/components/Home.jsx), [SearchItems](https://github.com/ssemakov/pass/blob/7cd8c6c0bc395fa3676c151a84c1657cda8cb481/app/components/SearchItems.jsx) and [ItemsList](https://github.com/ssemakov/pass/blob/7cd8c6c0bc395fa3676c151a84c1657cda8cb481/app/components/ItemsList.jsx). Edit/delete are the requested missing features. Neither the old released app nor the proposed UIs were run for this comparison.

For A/B/D, preserve the recognizable unlock → search → select/reveal/copy workflow and the same four entry fields. Add edit/delete, clear locked state, a manual lock command, password change and encrypted backup/import flows. An all-items/empty-state view and search from the first character are proposed improvements, not compatibility requirements or a reason to send passwords into list responses. Keep saving/validation errors visible; never show success before the transaction or migration verification finishes.

## Comparison

| Dimension | A — SwiftUI/AppKit | B — Tauri/Rust + React | C — upstream KeePassXC | D — Wails/Go + React |
|---|---|---|---|---|
| Familiar Pass workflow | Same workflow and fields can be rebuilt; visual details change to native controls | Closest route to retaining the React card/search/form design | Same core tasks, but existing list/detail/group/editor workflow; expect user relearning | Same workflow and visual fidelity potential as B |
| UI code reuse | React components rewritten in Swift; field/layout ideas reusable | React concepts and selected presentation logic reusable after upgrading dependencies; remove database/Node access | No bespoke React UI reuse without a separate fork/product | Same presentation reuse as B; replace Electron/Node interactions with Go calls |
| Native macOS feel | Best fit for system controls, menus, focus and platform appearance; still requires deliberate design/testing | Native window/dialog/menu integration around HTML controls; CSS can resemble macOS but does not become AppKit controls | Established Qt desktop UI; verify macOS conventions in selected build; not a bespoke SwiftUI experience | Same native-shell/web-controls distinction as B |
| New CRUD UI | Build edit form and delete confirmation around existing field model | Build once in React; backend commands enforce transaction results | Already supplied by upstream; align history/recycle-bin behavior with deletion expectations | React UI can be shared with B; Go implements the service contract |
| Keyboard and accessibility | System controls provide a strong starting point; custom rows and secret actions still need VoiceOver/focus tests | Semantic HTML, accessible names, focus management and native menu shortcuts must be implemented and tested in WKWebView | Evaluate selected client’s existing shortcuts/VoiceOver behavior; upstream implementation reduces custom work but is not proof | Same frontend work as B; generated Go bindings do not provide accessibility |
| Styling/dark mode/window resize | Follow system controls; test 15 and 26 appearance and availability checks | Full CSS/design control; test dark mode, text scaling, selection and resizing on both WebKit versions | Upstream styles/settings; limited control without maintaining a fork | Same CSS possibilities and WebKit tests as B |
| Reveal/copy and lock behavior | Native event/clipboard integration; secrets may still exist in SwiftUI state | Frontend receives a password only for reveal/edit; copy can stay backend-owned; clear state and reject stale responses | Use and verify upstream lock, clipboard timeout and secret display behavior | Same visible behavior as B; Go owner handles copy and session generation |
| Customization cost | High rewrite cost, strongest native result | High initial bridge/security work, flexible shared frontend | Lowest UI ownership; substantial redesign would remove that advantage | Same frontend cost as B; backend effort depends on Go/CGo experience |
| Cross-platform UI | macOS app; other OS UIs require separate work | Shared web UI with platform-specific testing/integration | Existing desktop clients maintained upstream | Shared web UI with platform-specific testing/integration |

**B and D can look and behave essentially the same.** Rust versus Go mostly changes the backend and maintenance model. Neither framework inherently gives the better password-manager UI, guarantees accessibility, or removes the need to test macOS’s WebView. Native unlock/password-change controls can be considered for either, but a file dialog alone is not a native secure password-entry implementation.

## V1 workflow contract

| Task | A/B/D custom app | C adoption check |
|---|---|---|
| Unlock | Pick vault locally; enter password; consistent error handling; no remembered key required | File + master password must work on a clean account |
| Search and browse | Return metadata only; retain selection predictably; no password prefetch in cards | Confirm equivalent find/select workflow and field mappings |
| Create/edit | Same four fields; represent unchanged / explicitly empty / null distinctly. A masked password is a display state, never a replacement value. Omitted password update preserves the existing secret; explicit blank/replace is deliberate. Save confirms commit; cancel discards draft | Verify native values after edit/save/reopen. Treat legacy timestamp/null metadata as import provenance, not current state |
| Delete | Explicit confirmation; remove active record in a transaction; no secure-erasure claim | Configure/verify recycle bin, history and backup retention; explain their effect |
| Reveal/copy | Explicit user action; conceal on lock; clipboard timeout clears only still-owned content | Verify upstream behavior on 15/26 and after sleep/screen lock |
| Migration | Untouched encrypted backup → fresh encrypted destination → every-entry comparison → success; discard incomplete output and restart | Same contract, including native field fidelity and no plaintext disk staging |
| Change master password | Native flow; new encrypted candidate, verify and safely replace with all old handles closed; old backup remains untouched; verify new password works and old password fails on the new file | Verify upstream change/save/reopen flow and history/backup implications |
| Encrypted backup/restore | Save a consistent encrypted vault; restore from selected backup into a fresh destination; verify before success; show clear errors without exposing data | Exercise upstream backup/copy/open behavior; a copied closed KDBX plus its password must work without remembered local keys |
| Lock and errors | Clear visible secrets immediately, acknowledge full lock after backend cleanup; no late callbacks or false save success | Exercise equivalent upstream lifecycle paths and restore behavior |

For evaluation, use the same synthetic vault and task script on macOS 15 and 26. Check keyboard-only completion, VoiceOver labels, edit cancellation, unchanged/blank/null password handling, masked-placeholder rejection, delete confirmation, password change, file-only backup/restore, dark mode, resizing, long/Unicode values, and lock during reveal/save. For B/D run against the packaged macOS WebView, not only a browser development server. C’s imported provenance must never overwrite newer native values on restore/reopen; require a separate old-archive import operation if such a feature is ever requested. A normal backup restores its current native contents, not a replay of import metadata. These checks are proposed acceptance work; no pass result is claimed here. For password change and restore, also test cancellation/disk failure: leave the existing valid vault/backup intact and never report success for an unverified candidate. No pixel-identical legacy reproduction is required.

UI recommendation: A for the strongest native macOS experience; B or D for preserving a customizable React interface, with backend language chosen separately; C when using an existing manager’s UI is acceptable and minimizing ownership matters most.
